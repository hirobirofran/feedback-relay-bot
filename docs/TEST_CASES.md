## 1. 観点（家族目線の鍵穴）

Gemini 出力のまとめ読み時、以下 5 点だけ見る。これ以外は触らない:

1. **質問の具体性**: 絞れているか、雑でもう 1 回聞き直しが要る粒度ではないか
2. **開発者語の漏れ**: 「Issue」「リポジトリ」「ラベル」「コミット」等が文面に出ていないか
3. **Draft の地続き感**: 元の声と地続きか、別物に化けていないか（推測で膨らみすぎていないか）
4. **PII 拒否のトーン**: 叱る感じでなく、やんわり促しているか
5. **家族の続行意欲**: 読んで「返信続けたくなる」か、「しんどくて離脱する」か

## 4. Step 1 用 文言案（Step 1 実装前にここで合意したい）

本セクションは Step 1（PII 警告 + follow event あいさつ）の実装直前レビュー用。
承認されたら [src/app/api/line/webhook/route.ts](../src/app/api/line/webhook/route.ts) に反映する。

### 4.1 PII 注意文（全返信の末尾に 1 行差し込み）

```
※ 個人情報（お名前・住所・電話番号・健康情報など）は書かないでください。開発メモは公開リポジトリに残ります。
```

観点:

- 「個人情報」という一語だけだと家族がピンと来ない場合があるので、具体例を括弧で付けた
- 「公開リポジトリに残ります」で**なぜ書いちゃダメか**を示した。叱る感じにならないよう「書かないでください」→ 理由の順
- 後で Gemini 側ゲート（Step 3）も入るので、この警告が抜け漏れを拾い切れなくても二重防御の片方として機能する

### 4.2 follow event 初回あいさつ（友だち追加直後に送る）

```
こんにちは、食材管理アプリのフィードバック窓口です。
使ってみて気になったこと・改善してほしいことをカジュアルに送ってください。開発メモに記録します。

※ 個人情報（お名前・住所・電話番号・健康情報など）は書かないでください。開発メモは公開リポジトリに残ります。
```

観点:

- [CLAUDE.md §会話設計の初手ルール 1](../CLAUDE.md)「初回メッセージは決め打ち」のうち「食材管理アプリのフィードバック窓口です」の名乗りを踏襲
- 「カジュアルに送ってください」で**敷居の高さ**を明示的に下げる（家族が「どんなレベルのものを書いていいかわからない」で固まる対策）
- PII 警告を**ここにも出す**のが実質的な上流点（家族が初投稿する前に目にする位置）
- 長さは 3 文 + 注意書き。LINE の吹き出し 1 つで読み切れる粒度

### 4.3 成功時の返信文（Issue 起票後）

現状:

```
受け取りました、ありがとうございます。
開発メモ #{number} に追加しました。順に対応していきます。
タイトル：{title}
{url}
```

変更後（末尾に PII 警告を追加）:

```
受け取りました、ありがとうございます。
開発メモ #{number} に追加しました。順に対応していきます。
タイトル：{title}
{url}

※ 次の投稿でも、個人情報（お名前・住所・電話番号・健康情報など）は書かないでください。開発メモは公開リポジトリに残ります。
```

観点:

- 「受領 → 何が起きたか → 期待行動」の 3 要素を維持したまま PII 警告を足す
- 空行で「本題」と「次回への注意」を視覚分離
- 「次の投稿でも」で「毎回同じ注意が出る」ことの気まずさをやわらげる

### 4.4 失敗時の返信文

現状維持（PII 警告なし）:

```
ごめんなさい、うまく受け取れませんでした。少し時間を空けて、もう一度同じメッセージを送っていただけますか。
```

観点:

- 失敗時は**再送依頼**が主目的。PII 警告でノイズを増やすよりシンプルに
- 家族は直前のメッセージをそのまま再送するので、**直前メッセージに PII が含まれていた場合は漏れる** → これは Step 3 の Gemini 側ゲートで拾う前提

### 4.5 非テキスト時の返信文

現状維持（PII 警告なし）:

```
ありがとうございます、ただ今は文字のメッセージだけお受けしています。お手数ですが文字で送り直していただけると助かります。
```

観点:

- 「文字で送り直して」の指示が中心。ここに PII 警告を入れると焦点がボヤける
- 次に送られる文字メッセージには 4.3 の返信が付くので、結果的に警告は届く

## 5. Step 1 で決めた運用

- **PII 警告を初回だけ出す状態管理は Step 2 以降**なので、4.3 の成功返信では**毎回**警告を出す（冗長でも安全寄り）
- Step 2（Redis 会話状態）で「初回かどうか」を判定できるようになったら、4.3 を「初回 + 不定期のリマインダー」に調整検討
